# TernaKu implementation contract

Frontend: Next.js App Router + React + TypeScript, Bootstrap 5, Poppins. Static export deployable on any web hosting. Backend: CodeIgniter 3 + MySQL (InnoDB), separate origin `https://api.buildmanagement.id/ternaku`. UI Indonesian. Repository root contains frontend, `api/` contains CI3 application and SQL.

API base routes: `GET /health`, `POST /auth/login` `{email,password}`, `POST /auth/logout`, `GET /bootstrap`, `POST /commands` `{action,payload,request_id}`. JSON success `{data: ...}`, error `{error: string}` with appropriate status. Login data `{token,user}`. Bearer token; store hashed tokens in DB, expiration, active user check every request. Bootstrap returns State; employees see only their own production/pickup/sales/corrections, public prices/barns/feed plus safe user list and aggregated inventory/feed_inventory, their notifications, no admin audit. All amounts, IDs and dates match `src/lib/types.ts`. Prices are integer Rupiah/kg; weight precision 3 decimal places. Indonesia business timezone Asia/Jakarta.

Public registration: `GET /auth/registration-status` returns `{first_admin_required,setup_enabled}`; `POST /auth/register` accepts only `{name,email,password,password_confirmation,setup_token?}` and returns `{status:'active'|'pending',message}` without a login token. The Daftar button always remains visible on the login screen. Only an empty users table plus a valid owner setup key may create the first admin. Subsequent registrations are employees of the same farm, inactive and pending admin approval; clients cannot choose a role. Passwords preserve whitespace, require at least 12 Unicode characters, and cannot exceed 72 UTF-8 bytes. Pending/rejected users cannot authenticate even if their active flag is inconsistent. Registration status is stored in records; existing/manual accounts default to approved. Setup, duplicate emails, and approval are serialized with the command mutex; signup is limited per IP and email. Owner setup keys/passwords must never enter audit records or public deployment packages.

Commands return refreshed State unless the client requests a sale receipt. For `sale.create` the frontend sends `response_mode: "compact"` and the signed-in user's `receipt_for_role` outside the payload. The `sale_receipt` response contains `command_result`, `sale`, `pickups` and `pickup_balances`. Open the receipt using the matching request ID and record ID. Retrying an identical payload with the same request ID returns the confirmed transaction. The API returns compact State if the role changed, and clients accept full State from older API versions.

Successful sales, harvests, egg receipts, returns, and positive warehouse additions create one `farm.activity` event for active accounts, including the recorder. An automatic harvest receipt creates one combined event per harvest. The command transaction writes inbox entries and queues delivery to registered devices. Each event includes the recorder's first name and weight only; command retries reuse the existing event.

When the API advertises `X-Ternaku-Photo-Upload: multipart`, send photo commands as one multipart request. The `command` field contains the JSON envelope with an empty `payload.photo` at its original position. The `photo` file contains the compressed JPEG, PNG or WebP, up to 1 MiB. JSON clients can use the equivalent data URL. Either format can replay the same request ID.

- production.create: `{date,items:[{category,eggs,kg,trays}],barn_id?,notes?,photo?,location?}`. Accept one or two distinct categories in one atomic, replay-safe harvest with a shared harvest_id. The legacy single-category payload remains valid. Positive eggs and actual kg are required in each supplied line. Respect harvest_auto_stock. A pending category enters stock on its own production.receive.
- `stock.reconcile` requires an admin, a reason, and one or two distinct egg categories. Send `{method,items:[{category,expected:{eggs,kg,trays},physical:{eggs,kg,trays}}],reason}` with the observed balance and the desired ending balance. For `add` and `subtract`, every selected category must change in the chosen direction. A `count` can confirm an unchanged balance. Older requests default to `count` and can omit trays from both snapshots to preserve the tray balance. A stale expectation returns HTTP 409. The ledger records the method, time, admin, reason, both snapshots, and signed deltas. Historical stock reports use dated movements and physical counts for the respective category in WIB.
- pickup.create: `{date,category,eggs,kg,trays,area,notes}`; own employee; locked stock validation both kg and eggs.
- pickup.return: `{id,eggs,kg,trays,notes}` returns unsold balance only, update returned_kg/returned_eggs; status derived.
- sale.create accepts `{date,customer,phone?,stock_source?,items:[{pickup_id?,category,eggs?,kg,trays,is_free?}],payment_method,paid,due_date?,notes,photo,expected_price_id?}`. The default source `pickup` uses the seller's own pickups. For `warehouse`, omit the pickup ID or send an empty string on every line. Admins and employees can sell directly from available warehouse eggs, kg and trays. Each sold category creates one signed stock movement linked to the invoice, including for free bentes. The receipt includes `pickups: []`, `pickup_balances: {}`, current `inventory` and the original sale's `stock_movements`. Corrections apply only the quantity difference per category. All sales require the customer's name and a documentation photo. If eggs are omitted, the server allocates a whole-egg estimate from current stock of the same source and category in the sale transaction, after reserving explicitly counted lines. Estimated lines include `eggs_estimated: true`. Selling the remaining weight uses the remaining egg count. Only an admin may use `is_free: true` to override a positive bentes price. An active bentes price of zero applies automatically to both roles. The server snapshots prices at submission and calculates totals in whole rupiah.
- sale.payment accepts `{id,amount,expected_paid?,method?}` for the owner or an admin. Clients send the paid total they saw when opening the form, and retry with the same request ID. Reject overpayment or a stale expected total (409).
- sale.due accepts `{id,due_date}` for the owner or an admin. An outstanding sale or purchase takes a YYYY-MM-DD due date on or after the invoice business date. The frontend asks for a due date on creation whenever a balance remains. The API also accepts older clients that omit it.
- price.create ADMIN: `{good_price,cracked_price,effective_at}` no deletes; notify all. active price <= now. effective datetime includes timezone or unambiguous local.
- user.create ADMIN: `{name,email,password,role,target}` hash password, unique email.
- user.update ADMIN: `{id,name?,active?,target?}` prevent self-disable/last admin lockout.
- user.approve ADMIN: `{id}` approve pending/rejected employee registration and activate the account.
- user.reject ADMIN: `{id}` reject pending employee registration. Generic user.update cannot activate pending/rejected registrations.
- Incentives: Coming Soon only; no calculations.
- barn.create ADMIN: `{name,type,capacity,notes}` type ayam.
- Cattle management: Coming Soon only.

- feed.create ADMIN: `{name,unit,min_stock}` unit kg, initial 0.
- feed.purchase ADMIN accepts `{date,supplier,items:[{feed_id,quantity,unit_price}],paid,due_date?,notes}`. Create the numbered invoice, calculate its total and add the purchased stock.
- feed.payment ADMIN accepts `{id,amount,expected_paid,method?}` for a supplier installment or final settlement. Check the expected total and outstanding amount under the invoice lock. This payment only updates the invoice. feed.due ADMIN accepts `{id,due_date}` on an open supplier invoice.
- Both invoice types retain `payments[]` with kind (`initial` or `installment`), amount, recording timestamp, actor and optional method (`cash`, `transfer`, `qris`). The paid amount of a legacy invoice can predate detailed history. Only display a payment time for an actual recorded entry.
- feed.use: `{date,feed_id,barn_id,quantity,notes}` consume quantity <= available locked feed balance.
- notification.read: `{id}` own notification only (or id all).
- correction.request: `{entity:'production'|'sale'|'pickup',id,reason,changes}` requires reason >= 5 chars. Employees unlocked own production may correct using correction.apply, otherwise request.
- correction.apply: `{entity,id,reason,changes}` ADMIN or own unlocked production. Validate all stock/ownership/financial invariants; reason >= 5, store before/after audit. Support production eggs/kg/trays/notes; pickup eggs/kg/trays/notes/area; sale notes/customer/items. Sale items must include all original lines exactly once as {id,eggs,kg,trays}; item price/category/pickup stay immutable. Recompute using historical prices, preserve paid, reject revised total below paid because refunds are not available. Validate all pickup balances after excluding original sale. Pickup corrections apply inverse quantity delta to warehouse and append a dated correction movement; cannot reduce below sold plus returned amounts.
- correction.review ADMIN `{id,approved}` applies safe allowed changes through same validation, record status.
- record.lock ADMIN `{entity,id,locked}`.

All writes atomic, nonnegative quantities, finite numbers, validation; server permissions mandatory. Reject over-selling, over-pickup, over-return/feed use. MySQL row locking and rollback. Employee sales restricted own; cannot override price, user_id, totals. Audit each write, mandatory correction reason.

Local demonstration is explicit in UI and uses localStorage; no fake API fallback. Demo only behind NEXT_PUBLIC_DEMO_MODE=true (default developer preview via .env.local, gitignored). Production config defaults false. Mode must clearly show DEMO. API env configured, real login if demo disabled. Demo data separate from live state.

Employee workspace prioritizes mobile harvest, sales, and warehouse good/cracked quantities with large controls and optional details. While visible, employees check prices every five seconds, with a prompt refresh on returning to the app or getting back online. After compact bootstrap, send its session-scoped `price_cursor` to `GET /sync/prices?since=<cursor>`. Apply `prices`, `notifications` and `read_notices` from each delta, then advance to its `cursor`. If `more` is true, immediately fetch the next page. Notification IDs distinguish updates with equal prices. Without a cursor the endpoint offers the compatible price snapshot. Full bootstrap is also available for role changes and periodic reconciliation. Reads cannot replace state from a newer mutation or session. Background failures preserve input and show the last successful refresh time. Price changes during a sale require renewed confirmation and server-side expected_price_id validation. The installable PWA uses the existing HTTPS frontend. Its service worker caches a public offline notice. Actual phone installation is completed by the user in their browser.

Authoritative types: src/lib/types.ts. Category good/cracked; Role admin/employee; string IDs; payment_method cash/transfer/qris/credit. All state collections use plural names in types. Employee bootstrap includes inventory {good:{eggs,kg,trays},cracked:{eggs,kg,trays}} and feed_inventory keyed by feed ID so warehouse/feed balances stay correct while individual rows remain private.
